# 多图与历史图片的视觉预算

2026-10-07 修复：视觉编码器按图片（视频按编码项）顺序执行，复用同一块工作区。此前前端把单个编码项容量当作整个请求累计上限，历史图片加新图片可能在进入模型之前被拒绝。

CLI 与 serve 使用相同参数：

```text
--vision --vision-device cuda
--vision-max-tokens 8192
--vision-request-max-tokens 32768
```

- `--vision-max-tokens`（原别名 `--vision-limit` 保留）：每个编码项的 token 上限，也是原生 CUDA 视觉工作区的容量依据。静态图片会按这个上限自动缩小；无法满足编码项上限时明确拒绝。
- `--vision-request-max-tokens`：整个请求，包括历史消息，累计的视觉 token 上限。默认 32768；不扩大 GPU 视觉工作区或 KV 视图预算。单张上限和累计上限独立；累计上限可以比单张上限小，此时按累计规则拒绝。
- 两张各 8192 token 的图片累计为 16384，可以通过默认累计预算。累计超过 32768 时仍然拒绝，错误指出累计参数并注明包含历史图片。
- 视觉 token 仍占总上下文；原来的上下文长度、最多 16 个媒体项、媒体大小和解码像素限制继续生效。

这不是无限图片支持。前端仍预处理历史图片，随后运行时按内容/前缀身份决定 KV 复用，已复用的图片不再重新编码。没有新增 GPU 图片 embedding 缓存，也没有修改 dense 内核、分派、MTP 或 KVMem 页选择。

累计上限主要约束主机内存：当前 FP32 patch 数据每个视觉 token 约 24 KiB，默认 32768 token 对应最多约 768 MiB 最终 patch 缓冲，准备过程中还有原图、临时数据和复制的峰值占用。多个待处理请求分别持有自己的数据；增加累计上限需要考虑总主机内存与排队请求。

验证包含同一消息多图、历史图加新图、累计边界和超限、prepare/count 一致、单图缩放、CLI/serve 默认值及非法参数；另用两张 4096×2048 图验证每张 8192、累计 16384 的真实预处理规模。无需同时加载两份模型。

GPU 编码数值、视觉权重来源和 KV 缓存语义沿用原版。运行中的旧服务不会自动换成新二进制；关闭旧服务后重新启动新包才生效。
